# 결정 기록

두 부분으로 나눈다.
- **키트의 기본 결정** — 이 키트가 처음부터 정해 둔 것과 그 이유. 프로젝트가 이것을 바꿀 때는 지우지 말고 아래 "프로젝트 결정"에 바꾼 내용을 적는다.
- **프로젝트 결정** — 키트를 쓰는 프로젝트가 직접 정한 것. 규칙을 바꿀 때는 여기에 날짜·결정·이유를 먼저 적고, 해당 규칙 문서를 고친다.

HIG와 다르게 정한 것은 **HIG와 다름**으로 표시한다.

## 키트의 기본 결정

### 글자

| 결정 | 이유 |
|---|---|
| **데스크톱(761px 이상) = macOS HIG, 폰(760px 이하) = iOS HIG** | 목표는 맥 네이티브 앱처럼 느껴지는 웹 앱. HIG는 플랫폼마다 자기 크기를 쓰도록 한다. 데스크톱에 iOS 값(본문 17)을 쓰면 네이티브 앱보다 뭉툭하다 |
| 웹의 1 CSS px = Apple의 1pt로 본다 | Retina 맥의 Safari에서 13px는 네이티브 13pt와 같은 크기로 보인다 |
| 데스크톱 글자는 **macOS 원값 그대로** — 본문 13, 최소 10, 긴 본문도 13 | 네이티브 앱과 같은 밀도. 한글 보정안(최소 11, 읽는 글 15)은 고르지 않았다 |
| 폰 글자는 iOS 기본(Large, 본문 17)이 아니라 **iOS "작게"(Small, 본문 15)** | 실제 폰에서 Large는 글자·칩·카드가 모두 뭉툭하게 커서 카드 하나가 화면 절반을 차지했다. Apple 공식 크기 단계 안에서 한 단계 줄인 값이다 |
| 같은 토큰 이름이 760px에서 값만 바뀐다 (`--fs-* / --lh-* / --tr-*`) | 페이지 코드는 크기가 아니라 역할(제목·본문·메타)만 고른다. 폰 전용 크기 규칙이 생기지 않는다 |
| 크기만 바꾸는 `--fs-*` 토큰을 따로 둔다 (`--t-*`는 `--fs-*/--lh-*`로 조합) | `font-size`만 바꾸던 규칙을 `font` 축약형으로 바꾸면 굵기·줄높이가 초기화된다 |

### 색과 면

| 결정 | 이유 |
|---|---|
| 배경·카드는 **iPhone 설정 앱과 같은 값**: 라이트 `#f2f2f7` / `#fff`, 다크 `#000` / `#1c1c1e`, 떠 있는 면 `#2c2c2e` | Apple 공식 회색 단계(gray6·gray5)와 같다. 다크에서 떠 있는 면일수록 한 단계 밝게 — **HIG(iOS)와 같음** |
| **강조색 하나**, 링크도 강조색 | 버튼은 강조색·링크는 다른 파랑이면 한 화면에 파랑이 둘이 된다. HIG "같은 색을 다른 뜻으로 쓰지 않는다". 인디고 링크 대비: 라이트 5.1 : 1, 다크 카드 위 4.85 : 1 |
| 기본 강조색 **Indigo** | 키트의 기본값. 프로젝트는 시스템 색 중 하나로 바꿀 수 있다 — 바꾸면 링크 대비를 다시 재고 "프로젝트 결정"에 적는다 |
| 강조색을 섞은 회색 면을 만들지 않는다. **카드 안 회색 상자 대신 0.5px 구분선** | 라이트에서 카드 안 회색이 페이지 바탕과 같은 색(1.1 : 1)이라 구멍처럼 보였고, 다크에서는 강조색이 섞여 탁한 회색이 됐다. 설정 앱은 카드 안을 구분선으로만 나눈다 |
| 보조 글자 라이트 `#6e6e73` | iOS 측정값이 4.5:1 대비를 넘지 못해 apple.com 값으로 조정 |
| 테마: **자동(기기 설정) + 앱에서 바꾸기**(자동·라이트·다크), 기본값 자동 — **HIG와 다름** | HIG는 앱 전용 외관 설정을 두지 말라고 하지만, 여러 사람이 쓰는 공용 기기를 고려해 허용. `AppUI.setTheme()`이 바꾸고 `'app:theme'` 이벤트를 보낸다 |
| 사용자가 고르는 색(사람 색 등)은 **자유 선택** — 테마를 따르지 않는 유일한 예외 | 자기 색을 고르는 재미를 지킨다. 대신 표시용으로만 쓰고, 그 위의 글자색은 자동으로 고른다 |
| 그 밖의 데이터 색은 **시스템 색 이름으로 저장**하고 `rgb(var(--이름))`으로 그린다 | 다크·고대비를 따라가게. hex 팔레트를 저장하면 여러 계열이 섞이고 테마를 따라가지 않는다 |
| 분류 태그 색은 축 안의 순서대로 12색, 관리 화면에서는 시스템 색 목록에서만 고른다 | 색이 적은 팔레트(11색 등)는 금방 같은 색이 겹친다. 아무 색 고르기를 두면 테마를 따르지 않는다 |
| 기본 배정 색에서 회색을 뺀다 | 회색은 "없음·기타"의 뜻 |
| 캔버스 차트는 `'app:theme'`을 받아 다시 칠한다 — 테마를 바꿀 때 새로 고침하지 않는다 | WebGL·캔버스 색을 불러올 때 한 번만 계산하면 새로 고침이 필요해진다 |
| 히트맵 진하기는 요소 투명도 대신 `color-mix()` | 고대비·다크에서 바탕과 섞이지 않게 |

### 모양 — 둥글기·간격·머티리얼·크기

| 결정 | 이유 |
|---|---|
| 둥글기 6단계: **20**(카드·시트) · **14**(팝오버·메뉴) · 10 · 8 · 4 · 완전 | 동심원 규칙(메뉴 14 − 여백 6 = 항목 8). 4는 체크박스·키 표시처럼 작은 사각형용 — 8은 너무 둥글다 |
| 카드 둥글기 20, **카드 사이 24**, 카드 제목 15 (Title 3) | 설정 앱처럼 또렷하게 보이는 것은 넓은 간격·큰 둥글기·분명한 제목에서 온다 |
| **0.5px 카드 테두리는 넣지 않는다** | 3배 확대해도 차이가 거의 보이지 않는다. 면은 색 차이와 간격으로 나눈다 |
| **유리는 내비게이션·컨트롤에만**, 콘텐츠에는 불투명 면 | HIG: 유리는 내비게이션 층에만, 콘텐츠와는 스크롤 가장자리 효과로 분리 |
| **폰에서는 유리 흐림을 끈다** (불투명 바·메뉴) | 흐림은 폰 GPU 비용이 크다. 아이폰의 브라우저는 모두 WebKit이라 데스크톱 측정 환경에서 비용을 재기 어려워 안전하게 끈다 |
| 바 아래에 붙는 줄(피드 탭 등)은 글 위에 뜬 유리 캡슐 대신 불투명 줄 + 스크롤 가장자리 효과 | 같은 HIG 규칙 |
| 데스크톱 컨트롤 기본 높이 28 (작은 22, 큰 34), 폰 44 | HIG macOS 기본 컨트롤 28×28, 최소 20×20. iOS 누르기 영역 44 |
| 화면 폭 기준점 2개: 760(폰) · 900(1단) | 기준점이 여러 개 흩어지지 않게 둘로 정한다. 칸 폭에 따라 바뀌는 배치는 컨테이너 쿼리로 |
| 2단 레이아웃의 사이드 폭 340 | 320 / 340 / 360이 섞이지 않게 하나로 |
| 아바타 4크기(20·28·36·56), 이니셜은 폰에서도 고정 | 크기마다 덮어쓰기가 생기지 않게 넷으로 정한다. 폰에서 이니셜이 커지면 원 안에서 두 줄로 깨진다 |

### 앱 구조

| 결정 | 이유 |
|---|---|
| 데스크톱은 위에 붙은 **얇은 반투명 상단 바** (macOS 앱의 사이드바 구조는 쓰지 않음) | 화면을 넓게 쓴다. 사이드바도 검토했으나 상단 바를 기본으로 정했다 |
| 폰은 **아래 탭 바**(5개까지) + 위 얇은 한 줄, 내 페이지는 오른쪽 위 아바타에서 | HIG가 권하는 iOS 구조. 탭은 5개까지라 내 페이지는 아바타로 (App Store·음악 앱과 같은 방식) |
| 전역 검색(돋보기 + `/`·⌘K)과 목록 필터를 나눈다 | 상단 바의 큰 검색창은 사실상 한 목록의 필터가 되기 쉽다 |
| 시트 버튼은 **아래 오른쪽 [취소] [주요]**, 머리의 취소·완료는 폰 전용 | 앞은 macOS 시트의 배치, 뒤는 iOS 방식 |
| 캔버스 배치 계산은 화면 밖에서 한 번에 계산 후 한 번 그리고, 다른 페이지로 가면 멈춘다 | 그리면서 수백 번 돌리면 CPU가 계속 쓰이고 다른 페이지에서도 남는다. 대신 처음 여는 시간이 조금 늘어난다 |

### 컴포넌트와 코드

| 결정 | 이유 |
|---|---|
| `tokens.css` → `components.css`를 다른 CSS보다 **먼저** 불러오고, 컴포넌트 선택자는 **`:where([data-ui]) .ui-x`** (우선순위 = 클래스 하나) | 컴포넌트가 페이지 규칙보다 늦게·높은 우선순위로 오면 페이지에서 배치를 바꾸려고 `!important`나 긴 선택자가 필요해진다 |
| `ui-btn` 기본 모양 = 회색 바탕 + 검정 글자 | macOS 푸시 버튼. 강조색 글자 버튼은 iOS 방식 |
| 문장 안 글자형 버튼 `.ui-btn.text` | `.plain`은 높이·여백이 있어 문장 흐름을 깬다 |
| 선택 상태는 `.on` 같은 클래스 대신 **`aria-pressed` / `aria-current`** | 화면 읽기 프로그램이 켜짐·현재 위치를 알 수 있다. 모양과 접근성 상태가 어긋나지 않는다 |
| 칩은 켜고 끄는 필터만. 동작하는 칩은 `ui-btn small`, 투표는 `ui-btn small` + `aria-pressed` | 같은 알약 모양이 다른 역할을 하지 않게 |
| 기본 입력창(`input`·`textarea`·`select`)은 **우선순위 0 규칙**으로 모두 같은 모양 | 입력창마다 클래스를 붙이지 않아도 되고, 문맥 규칙은 폭만 남는다 |
| 행은 `ui-row` 하나 (+ `.two` `.rich` `.ruled`), 페이지 클래스는 칸 배치만 | 높이·여백·호버·구분선·글자를 한곳에서. 데스크톱 행 28px |
| `!important`는 `[hidden] { display: none !important }`만 | 브라우저 기본 동작을 바로잡는 표준 방식. 그 밖의 경우는 선택자 우선순위를 바로잡는다 |
| **페이지 코드에 hex를 쓰지 않는다.** hex가 꼭 필요한 데이터 표는 `// design-lint: off (이유)` … `// design-lint: on`으로 감싸고, 그 위치를 "프로젝트 결정"에 적는다 | 정당한 예외를 숫자에 묻어 두지 않고 위치를 드러낸다. `design_lint.py`가 검사한다 (설정은 `design_lint.json`) |
| 브라우저 `confirm()`·`prompt()`·`alert()` 대신 `AppUI.confirm()`·`AppUI.sheet()` | HIG 알림·시트 규칙(제목 = 질문, 구체 동작어 버튼)을 지킬 수 있다 |
| 견본 페이지(`specimen.html`)를 먼저 만들고 확정한 뒤 화면에 적용 | 실제 화면을 건드리기 전에 라이트/다크/고대비를 나란히 검토한다 |
| 큰 CSS 정리는 화면 스크린샷의 픽셀 비교로 확인 | 의도하지 않은 변화(예: CSS 순서 변경)를 숫자로 확인한다 |

### 글쓰기

| 결정 | 이유 |
|---|---|
| 버튼 문구는 **Apple 한국어 방식** (저장·삭제·편집·추가·완료·취소, 대상이 필요하면 "대상 + 동작어") | iOS·macOS 한국어 UI와 같은 말. "~하기"보다 짧다 |

## 프로젝트 결정

키트를 쓰는 프로젝트가 정한 것을 날짜순으로 적는다. 키트 기본과 다르게 정한 것은 **키트 기본과 다름**, HIG와 다르게 정한 것은 **HIG와 다름**으로 표시한다.

| 날짜 | 결정 | 이유 |
|---|---|---|
| 2026-01-01 (예) | 강조색 Indigo → Blue — **키트 기본과 다름** | 브랜드 색과 가장 가까운 시스템 색. 링크 대비를 라이트·다크 카드 위에서 다시 잼 |
